# 플토 UI 등록·수정 운영 사례

2026-11-04 사례 상품 A 및 사례 상품 B 작업에서 확인했다. 화면 ID, 좌표, 브라우저 연결 ID, 계정·배송 템플릿 번호는 실행마다 다시 확인하며 공유 지침에 고정하지 않는다. 아래 성공 범위를 넘어 해결됐다고 주장하지 않는다.

## 파일 첨부 실패와 건별 등록 대체

- 엑셀은 먼저 [excel-bulk-registration.md](excel-bulk-registration.md)의 성공 경로를 사용한다. 사례 상품 B는 새 Chrome 탭의 파일 입력에서 Space로 선택기를 열고 Microsoft Excel로 호환 저장한 파일을 첨부하여 실제 일괄등록에 성공했다. 아래 사례 상품 A의 건별 등록 사례는 이전 대체 경로이며, 엑셀 등록이 현재도 불가능하다는 뜻이 아니다.
- 엑셀 준비/호스팅 완료, 파일 선택, 업로드 접수, 플토 상품 생성, 마켓 전송을 별도 단계로 기록한다. 파일 선택 실패는 상품 등록 실패가 아니다.
- 먼저 현재 도구의 업로드/문제해결 문서를 읽는다. 파일 URL 접근 권한이 이미 확인됐으면 같은 설정을 다시 요구하지 않는다. 동일한 파일 선택 시간초과를 반복하지 않는다.
- 바인딩된 Chrome 탭의 최신 AX/DOM 또는 스크린샷으로 실제 업로드 버튼을 찾는다. 대표사진 영역의 중앙은 미리보기, 연결 아이콘은 FTP 화면일 수 있다. 스크린샷에서 확인한 업로드 아이콘을 누르기 **전에** `waitForEvent('filechooser')`를 걸고, 반환된 선택기에 `setFiles(절대경로)`를 사용한다. 당시 이 방법으로 대표 이미지 1/2/3/4개 구성 업로드에 성공했다. 과거 좌표를 재사용하지 않는다.
- 별도 Windows 앱 제어에서 현재 URL 검증이 차단되면 그 경로로 강행하지 않는다. URL이 확인되는 바인딩된 브라우저 탭 제어가 정상인 경우 그 지원 경로를 사용한다. 이것을 Windows 네이티브 연결 자체의 수리 성공으로 보고하지 않는다.
- 엑셀 조작이 계속 실패하지만 사용자가 상품 등록을 승인한 상태라면 플토 건별 등록 UI로 동일 데이터를 입력할 수 있다. 사례 상품 A은 이 대체 경로로 등록했다. **엑셀 업로드 성공으로 기록하면 안 된다.** 원본 계산기·상품 자료는 수정하지 않는다.
- 엑셀 경로를 쓰는 경우 일반/단일 공식 양식을 구분하고, 머리글 행·필수 열·계정·카테고리별 옵션 사양을 검증한다. 업로드 오류는 해당 항목만 고친다. 이미 생성된 상품이 없는지 재확인 후 재업로드한다.
- 상세 HTML은 소스 모드 편집칸에 넣고 저장 후 이미지 구성을 확인한다. 호스팅 URL은 기존 체크포인트에서 재사용한다.

## 한 구성당 마스터 하나와 수량별 묶음

사용자가 같은 구성은 공통 마스터로 묶고 쿠팡·토스를 제외한 마켓은 수량별 개별상품을 요청했을 때 적용한다.

1. 기존 상품번호·계정·판매자관리코드 목록을 먼저 기록한다. 같은 1개 구성의 여러 마스터는 `작업 → 판매자관리코드 선택 수정`에서 기존 공통 코드를 입력하고 `중복확인`의 이동 대상 안내를 확인한 뒤 합친다. 사례 상품 A에서는 기존 마켓 상품번호를 유지한 채 통합됐고 빈 마스터가 목록에서 사라졌다. 이 결과를 확인하며 별도 삭제 작업을 추가하지 않는다.
2. 추가 수량은 쿠팡·토스를 제외한 승인 마켓만 복사한다. 일반상품과 ESM을 각각 복사했다면 생성된 공통 코드로 합친다. 쿠팡·토스가 포함된 전체 마스터를 무심코 복사하지 않는다. 이후 이미 대상 마켓만 포함된 묶음 마스터를 복사하면 다른 수량도 만들 수 있다.
3. 수량별 마스터명, 대표사진, 상세 HTML의 상품사진, 판매가·시중가, 단위가격의 실제 묶음 수량을 수정한다. 개당 용량과 총수량을 구분한다. 각 마켓 판매가는 계산기 값을 개별 반영한다. 공통 가격을 적용한 뒤에는 스마트스토어·카카오·셀러허브 등의 개별 가격을 다시 대조한다.
4. 마스터 저장 시 `연동된 쇼핑몰 상품 정보도 공통 수정 → 선택 항목`을 사용하여 실제 변경한 필드만 선택한다. 상품명/이미지/상세설명/가격/단위가격 등을 무조건 모두 선택하지 않는다. 공통 제조사 수정은 `모델명/브랜드/제조사` 묶음 안의 나머지 값도 맞는지 확인한다.
5. 마스터 저장은 플토 내부 저장이다. 마켓 반영은 별도 수정 전송과 최종 결과 확인이 필요하다. ESM은 화면이 요구하는 옥션·지마켓 쌍을 함께 선택한다.

사례 상품 A 검증 구성: 1개 마스터에는 9개 마켓, 2/3/4개 마스터에는 각각 7개 마켓. 총 4마스터/30레코드이며 쿠팡·토스는 1~4개 옵션을 갖는 기존 상품 하나씩만 유지했다. 이는 당시 계정 구성 예시이며 다른 상품의 마켓 수를 고정하지 않는다.

## 승인한 시중가·제조사 표기

- 사용자가 셀러허브·토스에 승인한 가산 패턴은 판매가 5만원 구간마다 5천원 증가다. 적용 예: 48,900→53,900 / 97,700→107,700 / 146,500→161,500 / 195,300→215,300. 계산식은 양수 판매가 `P + 5000 × ceil(P / 50000)`로 기록하되, 정확히 50,000/100,000 등 경계값은 당시 사례에 없었으므로 사용자 기준이 불명확하면 그 경계만 확인한다.
- 이 기준이 현재 상품에 승인돼 있을 때 적용한다. 새 상품에 임의의 할인 근거나 시중가를 만들어 적용하지 않는다. 기존 판매가는 유지한다.
- 토스의 플토 `시중가`는 공통 정상가다. 당시 옵션표와 추가항목에는 옵션별 시중가 입력란이 없었다. 사례 상품 A의 공통 정상가 전송 성공을 옵션별 목표값 적용 성공으로 확대하지 않는다. 이후 사례 상품 B에서 토스 판매자센터의 옵션별 정상가 입력·저장·재조회에 성공했다. 승인된 구간별 가산 기준이 있으면 전송 후 각 옵션의 실제 정상가를 확인하고, 차이가 나는 옵션만 판매자센터에서 보완한다. 옵션 판매 추가금액을 바꿔 시중가를 흉내 내지 않는다. 마켓 직접 보완값과 플토 저장값의 차이를 receipt에 기록하여 다음 전체 수정 전송이 보완값을 덮어쓰지 않게 한다. 세부 사례는 [excel-bulk-registration.md](excel-bulk-registration.md). [플토 토스 상품등록 안내](https://www.plto.com/customer/HelpDesc/gmp/15201/) 참고.
- 사례 상품 A에서 승인한 제조사 표기는 문자 그대로 `브랜드 협력사`였다. 이를 실제 브랜드명으로 치환하지 않는다. 고시의 제조업자·책임판매업자를 같은 값으로 자동 변경하지 않는다. 다른 상품에는 그 상품의 근거/현재 승인값을 사용한다.

## 승인대기와 상품 상태만 동기화

- 당시 `상품전송`은 판매대기/수정대기, `부분수정`은 수정대기만 허용했다. 승인대기 표시가 오래됐을 때 상품 전체 동기화로 해결하려 하지 않는다.
- 대상 상품만 선택하고 `상품동기화`에서 **상품 상태만 선택**한다. 기본 선택된 판매수량·판매종료일·판매가격을 명시적으로 해제한다. `마지막 선택값 기억`도 필요 없으면 해제한다. 실행 전 최신 화면에서 각 체크의 해제 상태를 확인하고 나서 동기화한다. 한 호출에서 불명확한 토글과 실행을 묶지 않는다.
- 이 방법은 저장된 가격·수량을 마켓 값으로 덮어쓰지 않고 실제 마켓 상태를 확인한다. 사례 상품 A 쿠팡·토스는 동기화 후 판매중으로 확인되어 저장된 변경을 다시 저장하고 수정대기 상태로 만든 다음 기존 상품 수정 전송에 성공했다.
- 동기화 후에도 승인대기이면 실제 대기 상태로 기록한다. 임의로 판매중 상태를 만들어 전송하지 않는다. 수정 성공 후 다시 승인대기가 될 수도 있다. 접수·전송 성공·승인대기·판매중을 각각 기록한다.

## 결과 검증과 재개 기록

- UI의 도구행/체크박스와 데이터행이 분리되어 있으므로 최신 전체 목록에서 코드·계정·구성으로 대응시킨다. 가상 스크롤로 요소가 분리되면 해당 상품으로 검색을 좁힌다. 오래된 행 번호나 도구 ID를 재사용하지 않는다.
- 저장/검색 직후에는 이전 목록이나 로딩 화면이 잠깐 남을 수 있다. 최신 상태가 확인될 때까지 결과를 단정하지 않는다. 원본 선택 항목을 전부 지울 때 빈 문자열 붙여넣기가 동작하지 않으면 해당 입력칸에서 전체선택 후 삭제한다.
- 전송 전 대상 건수와 신규/수정 구분을 확인한다. 작업관리 최종 성공/실패, 새로 조회한 마켓 상품번호, 판매상태를 함께 기록한다. 성공한 기존 상품은 새 번호를 만들지 않는다.
- 실패 마켓만 원인에 맞게 처리한다. 사례 상품 A 셀러허브는 브랜드 검색 불일치로 1~4개 구성만 보류했고 다른 마켓은 계속했다. 이전 상품의 사용자 보류를 새 브랜드에 자동 적용하지 않는다. 브랜드 신청·문의는 제외 범위를 유지한다.
- 로컬 receipt와 자동화 state의 해당 상품을 함께 갱신한다. 구성별 마스터, 마켓별 번호/가격/상태, 작업번호, 미완료 필드, 검증 출처, 원본 변경 여부를 남긴다. 기존 요약 파일의 오래된 승인대기·보류 수치도 최신 확인값과 일치시킨다. 자신의 잠금만 해제한다.
